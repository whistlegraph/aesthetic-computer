# YOUR DIMENSION: HOW THE MODEL WORKS

You own procedure, tool use and finishing — not what makes a piece good. Trace
the run and match each failure to the cheapest fix:

- A TOOL ERROR (a rejected write, a stale revision, an ac_api miss): say what
  the model should do instead, once, with a point where it stops retrying.
- A CHECK IT IGNORED OR NEVER MADE: say when to read ac_preview and what
  "done" requires — a save that only parses is not a working piece.
- WASTED ROUNDS (re-reading what is already in context, rewriting the whole
  file for a small change, narrating instead of writing): name the shorter path.
- A FINISH IT CLAIMED WITHOUT EVIDENCE: tie the claim to the check that proves it.

Do not add rules about what a piece should look or sound like. A parallel
candidate owns that; stay on how the model works.

# Menu Band — architecture and source review

2026-09-23. Read against the working tree, not HEAD. `SingerFace.swift` was
edited during the review (`faceAlpha` → `skin`, `SingerGaze.swift` added), so
line numbers in §1 drift by a few; the citations were re-taken after that edit.

The question that prompted this: three cosmetic changes this morning — face
panel opacity, caption jitter/sway/pop, caption stroke and glow — each cost a
Swift edit, a five-minute universal build on neo, and a 34 MB bundle pushed to
two machines, one of which cannot compile Swift at all.

Three things are true and each one alone would justify the work:

1. Nearly every visual decision the face and captions make is a float literal
   in a `draw` method. Seven payload keys reach them; about 140 constants do not.
2. `trio.mjs` does not forward cosmetic keys on a **sung** voice at all. The
   `faceAlpha: 0.7` in `scores/trio-wake.mbscore` has never reached a machine.
3. `install.sh` does not fail when `swift build` fails. On a member with a
   working previous build it re-signs and installs the **stale** binary and
   exits 0. That is the blueberry symptom, reproduced below.

## 2. A hot-updatable behavior layer

### The constraint nobody can design around

`SingerPreparedPerformance.fingerprint` (SingerPreparedPerformance.swift:20-24)
hashes the **entire payload** minus four scheduling keys. A prepared take is
accepted at cue time only if the fingerprint still matches
(`:68`, `AppDelegate.swift:4765-4775`). So **any cosmetic value carried on the
payload invalidates every prepared render when it changes.** Recoloring a
caption would force a re-render of the whole show.

That settles it: looks must live somewhere the fingerprint does not see.

### Options

**(i) More payload keys — status quo extended.** Cheapest per key and it works
today for the eight that exist. But the payload is one `k=v;k=v` line shipped
through `ssh host "MB_KV='…' /tmp/mbpost"` (`trio.mjs:121`) with `;` and `=`
stripped from values (`:428`, `trio-payload.mjs:5`). Forty cosmetic keys on
every cue is unreadable and unauditable, it breaks prepared renders, and the
conductor still has to re-send the whole cue to change a color. Keep it for
one-off overrides. Not the spine.

**(ii) A watched style document per member. — recommended.** A small JSON file
on disk, hot-reloaded, with `.mbscore` voices naming a style. No compiler on the
member, so frisbee works. The repo already has the pattern:
`MenuBarFit.swift:326-372` does atomic-write + poll + `Codable` state and command
files across processes, and it has held up.

**(iii) An interpreted expression language.** Tempting, because the repo already
contains a Swift KidLisp — `Sources/MenuBand/KidLisp/` at 1,455 lines
(KLEvaluator 535, KLFramebuffer 313, KLColor 179, KLLexer 123, KLParser 110,
KLCLI 112, KLRNG 34, KLRuntime 29, KLExpr 22) — and it is currently dead
outside `--kidlisp-render` (`main.swift:6`). But it renders into a pixel
`KLFramebuffer`, and the face renders through `SingerFaceCanvas` into a
triangle stream at display rate (`SingerFaceMetal.swift`, ~24k vertices
reserved at `:22`). Re-plumbing KL to emit geometry is a project, not a phase.
JavaScriptCore is strictly worse: a JS hop per glyph per frame, on the main
thread, next to lip-sync. Defer. Shape the style schema so a later scalar
`"expr"` field can slot in.

**(iv) Move presentation into a web view / the AC runtime.**
`AestheticWebWindow.swift` (301 lines) already embeds WKWebView, so the
mechanism exists. Rejected for the face: the mouth samples the singer's own
`AVAudioPlayerNode` clock in-process (`MenuBandSingerVoice.swift:107-114`), and
routing that through IPC puts a variable hop exactly where lip-sync lives.
A WKWebView also cannot be trusted at `.screenSaver` level with the same
latency. Reasonable later for a lower-stakes surface — a set list, a lyric
sheet — not for the singing face.

### The recommendation

A **style document**, watched on disk, named from the cue, with payload keys
surviving as per-cue overrides.

New files:

| file | what it holds | what it replaces |
|---|---|---|
| `Sources/MenuBand/Style/MenuBandStyle.swift` | `struct MenuBandStyle: Codable` with `Caption`, `Timing`, and `[String: FaceRig]`; every field optional; `merged(over:)` for layering | — |
| `Sources/MenuBand/Style/StyleDefaults.swift` | today's literals, moved verbatim, as `MenuBandStyle.default` | the constants in the two `draw` paths |
| `Sources/MenuBand/Style/FaceRig.swift` | per-member geometry as fields | `SingerFace.swift:460-461` and every `isBB ? … : isFrisbee ? … :` from `:497` to `:608` |
| `Sources/MenuBand/Style/StyleStore.swift` | singleton; loads `~/.config/menuband/styles/*.json`, 0.5 s stat poll (the `MenuBarFit` pattern), `style(named:)`, change notification | — |
| `bin/style-push.sh` | `scp` one JSON to each host, `shasum` back | a 34 MB bundle |

Call sites that change:

- `SingerFace.drawArtwork` — literals become `rig.<field>`; the two string
  compares disappear and a fourth machine becomes a JSON file.
- `SingerFaceView.tick` — motion constants become `style.motion.<field>`.
- `LyricCaption.show` / `.highlight` / `.hide` — the table in §1 becomes
  `style.caption.<field>`.
- `AppDelegate.swift:5067/5079/5085/5091` — the four cue offsets become
  `style.timing.{captionLead, lipLead, captionHold, faceHold}`.
- `AppDelegate.swift:4989/4990/5005/5006` — keep the keys, but as overrides
  applied on top of the resolved style, not as the only handle.

Payload contract: two new keys.

- `style=<name>` — which document to render under. Missing → `default`, logged.
- `styleHash=<first 8 of sha256>` — the member logs a mismatch instead of
  silently rendering something else. `trio.mjs` already does an ssh round trip
  per host for clock skew; one `shasum` more is free, and it turns "did the
  style land on frisbee?" into a printed table rather than a squint at a screen.

`.mbscore` schema: a voice gains `"style": "wake"`; a score gains an optional
top-level `"style"` all voices inherit. `singerPayload` forwards it.

Determinism at the downbeat is unaffected: the face is already a pure function
of `(member, accent, epoch, bpm, expression, articulation)` with deterministic
FNV jitter (`SingerFace.swift:402-410`, `LyricCaption.swift:146-147`). Adding a
`seed` field to the style makes that variation deliberate instead of fixed.

Audio-thread safety: the style is read on the main thread only — both consumers
already assert it. Nothing in the style reaches the render callback. DSP
(`sing*`) stays on the payload, where the prepared fingerprint can see it.

Push model: styles are pushed **ahead of** the show (one scp per host, a few KB)
and named **in** the cue. A change mid-rehearsal is `style-push.sh warmer neo
blueberry frisbee` — under a second, no build, no signature, no TCC re-grant,
and frisbee's broken toolchain is irrelevant because nothing compiles.

### Threading model

Three domains, and the boundaries are mostly right.

- **Main** — everything visual. `SingerFace`/`LyricCaption` assert it. All cue
  dispatch is `DispatchQueue.main.asyncAfter`, anchored once to a `(wall,
  uptime)` pair (`AppDelegate.swift:4866-4871`) so per-note drift cannot
  accumulate. This is good work and the jitter log at `:5124-5141` proves it.
- **`menuband.singer` serial queue** (`MenuBandSinger.swift:122`) — speech +
  WORLD + render, 0.5–3 s per line, completion hopped back to main. Correct.
- **Audio** — `KeyEventTap` runs `handleKey` on a background thread
  (`MenuBandController.swift:3336`) and hops to main for UI. The singer's tap
  (`MenuBandSingerVoice.swift:50-70`) computes RMS/ZCR on the tap queue and
  hops to main per ~23 ms buffer.

Rough edges, all minor:

- `MenuBandSingerVoice.swift:28` `static var lastTapLog` is read and written
  from the tap queue with no synchronization; with three sim voices those are
  three queues on one `Double`. Benign in practice, still a race.
- `NSLog` from the tap callback (`:68`) — takes a lock and allocates on a
  latency-sensitive queue.
- `MenuBandSingerVoice.face` (`:21`) is written on main
  (`MenuBandSynth.swift:71`) and read on the tap queue (`:62`). The write
  happens before `attach` (`MenuBandSynth.swift:71` then `:73`), so it is safe
  by ordering, not by construction.
- `MenuBandSynth.simSingerVoice` (`:68-77`) attaches five `AVAudioNode`s to a
  **running** engine at cue time. Tolerated by AVAudioEngine, but it can glitch
  on the downbeat, and the nodes are never released — a long sim session leaks
  them.

### Notification and payload surface

Sixteen distributed notifications, registered `AppDelegate.swift:1359-1540`.
Every observer passes `object: nil`, so any process on the machine can drive the
instrument. That is the design (it is the whole conducting story), but it means
the payload parser is the trust boundary and it is not defensive at it.

**Severity 2 — malformed `startEpoch` traps the process.**
`AppDelegate.swift:4870`:

```swift
return DispatchTime(uptimeNanoseconds: anchorUp.uptimeNanoseconds &+ UInt64(max(0, ns)))
```

`ns = (epoch − anchorWall) * 1e9`. A `startEpoch` in **milliseconds** (a very
easy conductor typo — `Date.now()` instead of `Date.now()/1000`) gives
`ns ≈ 1.8e21`, past `UInt64.max ≈ 1.8e19`, and Swift traps: *"Double value
cannot be converted to UInt64."* `Infinity` does the same. `NaN` is safe only
because `max(0, .nan)` returns `0`. Fix: clamp `ns` to a sane horizon (an hour)
and reject a non-finite epoch at `:4782`.

**Severity 2 — `bpm=0` traps in the singer's scheduling arithmetic.**
`AppDelegate.swift:4777` takes `bpm` unguarded. `:4785` guards its own use with
`max(1, bpm)`, but `SungLine` gets the raw value (`:4804`) and
`MenuBandSinger.swift:446` computes `first16 / 4 * (60.0 / line.bpm)` → `0 * inf`
= `NaN` → `AppDelegate.swift:4959` `downbeatEpoch + r.spanOffset` = `NaN` →
`MenuBandSingerVoice.swift:122` `.now() + lead` where `Int(Double.nan)` traps.
`SingerPreparedPerformance.swift:74` already guards this correctly
(`bpm.isFinite && bpm > 0`); `playFromInfo` should do the same.

Lesser parsing gaps, all one-liners:

- `handleSayNotification` (`:5255`) passes `rate` through unchecked for
  finiteness; `pitch`/`volume` are clamped, `rate` is not.
- `SungLine.init` (`MenuBandSinger.swift:40-47`) takes `lock`, `vibHz`,
  `vibCents`, `f0Floor`, `gapMs`, `sustainDb`, `shimmerFrames`, `legatoMs`
  straight from strings into the C core's params (`:431-434`) with no range
  check. `f0Floor = 0` or a negative `vibHz` reaches WORLD.
- Every numeric parse is `Double(x) ?? default`. `"abc"` degrades silently to
  the default with no log, so a typo'd key in an `.mbscore` is invisible until
  the show.

### The forwarding bug — cosmetics never reach a singing machine

`trio.mjs` has **two** payload builders and they disagree:

- Non-sung voices (`trio.mjs:476-478`) forward every voice key except a
  ten-name exclusion list. Full passthrough.
- Sung voices (`trio.mjs:442` → `trio-payload.mjs:2-26`) build an explicit
  **whitelist**: `bpm, startEpoch, program, notes, lyrics, singVoice,
  singVibratoHz, singVibCents, singLock, singF0Floor, singNoteGains,
  singLineGains, performance, singGapMs*, stemPath, wordsPath, captionColor,
  face, notes2-4, velocity2-4, title, sim`.

`faceAlpha`, `gaze`, `captionSize`, `caption`, `text`, and the four
`sing{Gap,Sustain,Shimmer,Legato}` overrides are **not in it**.

`bin/compose-wake.mjs:81` sets `faceAlpha: 0.7` on all three voices;
`scores/trio-wake.mbscore` carries it; `trio.mjs` drops it on the floor for
every sung voice, which is all three. It has never had an effect over the
conductor. The same key *does* work when the `.mbscore` is double-clicked
locally, because `AppDelegate.playScoreFile:4736` does a full passthrough:

```swift
for (k, v) in voice where k != "name" { info[k] = "\(v)" }
```

So a cosmetic tested by double-clicking the score silently vanishes when the
conductor sends it. That is almost certainly part of why this morning felt like
it needed a rebuild.

That same line has a second problem: `"\(v)"` stringifies a JSON value with
Swift's `description`. `noteGains: [[1, 0.78]]` becomes `"[[1.0, 0.78]]"`, which
`SingerPreparedPerformance.applyDynamics:27` (split on `/` then `,`) cannot
parse, and `performance` becomes a Swift dictionary description where
`SingerPerformance.decode:16` expects base64 JSON. Local `.mbscore` playback
therefore silently loses dynamics and the slide score.

**Fix:** delete `singerPayload`'s whitelist. Use the same exclusion-list
passthrough the instrumental path uses, plus the sung-specific defaults. One
builder, one contract, and every future cosmetic key works the day it is added.

### Build and deploy

**Severity 1 — `install.sh` does not fail when the build fails.** Reproduced:

```
$ bash t7.sh
error: Build failed
CONTINUED with STALE binary: './fakebin/MenuBand'
install.sh would now sign and ship this.
exit=0
```

The shape is `install.sh:168-185`:

```sh
build_slice() {
    swift build -c release --triple "${triple}" "$@" >/dev/null     # :171
    binpath="$(swift build … --show-bin-path)"                      # :173
    [[ -x "${built}" ]] || { echo "…build missing…"; exit 1; }       # :175
    …
}
ARM_BIN="$(build_slice "${ARM_TRIPLE}" arm64 MenuBand)"             # :188
```

macOS ships bash 3.2 (`/bin/bash`, which `#!/usr/bin/env bash` resolves to
here). Inside a function invoked from a command substitution in an assignment,
bash 3.2 does **not** honour `errexit` for an ordinary failing command — the
function keeps going. Verified: a `false` at the top of such a function still
reaches the line after it.

So when `swift build` fails, `build_slice` continues. `--show-bin-path` is a
path query and succeeds regardless. If the previous successful build's product
is still there — which it always is, since SwiftPM does not delete products on
a compile error — `[[ -x ]]` passes, the stale binary is copied, `lipo -archs`
confirms the right arch, `lipo` succeeds, `codesign` succeeds, and the script
prints `✓ built universal` and installs. On blueberry with a stale checkout
this installs yesterday's code and exits 0. The failure mode is exactly the one
the script's own comment at `:449-450` describes ("the stale image whistled a
payload the new code would have sung"), and the mitigation added there does not
catch it because the staleness is upstream of the swap.

Fix: capture the status explicitly.

```sh
if ! swift build -c release --triple "${triple}" "$@" >/dev/null; then
    echo "${product} ${arch}: swift build failed" >&2
    exit 1
fi
```

…and, for defence in depth, assert the copied slice's mtime is newer than the
newest file in `Sources/`.

**Severity 2 — the build lock destroys the staging-cleanup trap.**
`install.sh:48` sets `trap cleanup_stage EXIT INT TERM HUP`. `install.sh:71`
then sources `../bin/build-lock.sh`, whose `acquire_build_lock` sets
`trap 'release_build_lock' EXIT` and three more — **replacing** them. Verified:
in a script with both, only `release` runs on exit; `cleanup` never does.

So every failed install leaves a `~/Applications/.menuband-install.XXXXXX`
staging bundle behind — which `install.sh:34-36` itself identifies as "a bundle
with Menu Band's id sitting next to the real app, which is exactly what poisons
TCC." The sweep at `:37` cleans it on the *next* run, so the window is
one-run-wide, but on a machine where install keeps failing the window is
permanent. Fix: make `acquire_build_lock` append (`trap 'release_build_lock;
cleanup_stage' EXIT`) or have `install.sh` re-install its trap after the source.

**Severity 2 — `bin/ship-bundle.sh` can ship a stale tarball.** Line 7:

```sh
[ -s "$T" ] || tar -C "$HOME/Applications" -cf "$T" "Menu Band.app"
```

The tar is cached by existence. Line 26 removes `/tmp/menuband-ship.tar` — but
that line runs **inside the remote heredoc**, so it deletes the *remote* copy.
The sender's `/tmp/menuband-ship.tar` survives, and the next rebuild-and-ship
silently re-sends the previous build. Fix: build the tar unconditionally, or
key it on the bundle's mtime, and delete it on the sender at exit.

**Severity 2 — conducting requires a working Swift compiler on every member.**
`trio.mjs:107-114` `ensureTool` compiles `/tmp/mbpost` with `swiftc` on each
host, and `:366` makes that a precondition for sending that host anything.
Frisbee cannot compile Swift; the trio path there depends entirely on an
already-cached `/tmp/mbpost` surviving macOS's periodic `/tmp` cleanup. Worse,
`:108` caches by `test -x` with no version check, so editing `POSTER_SRC` never
takes effect on a host that already has the binary. Fix: ship a prebuilt
universal `mbpost` from neo via scp (it is a few dozen KB), key it by hash, and
fall back to `osascript`-based posting where no binary exists.

**Signing.** `install.sh:443-464` falls back to ad-hoc when the keychain is
locked in an ssh session. Correct call — the comment explains why aborting was
worse — but ad-hoc changes the cdhash every build, which drops Accessibility
and Input Monitoring grants on the member. That is an argument all by itself
for shipping one signed bundle from neo (`ship-bundle.sh`) rather than building
on each machine. `ensure_service_running` at `:587-588` returns 1 under
`set -e`, so a machine where the agent won't start does at least fail loudly.

**Universal build.** `install.sh:168-185` is two `--triple` builds plus `lipo`,
with an arch assertion on each slice (`:180-183`) after a real Xcode 27 bug
where `--show-bin-path` returned the same path twice. The care here is right;
it just sits downstream of the errexit hole.

### Tests

116 test functions across two targets, 70 of them in `ShapedownTests.swift`.
Excluding Shapedown: 46 tests for ~76,000 lines.

Nothing covers: payload parsing, `SungLine` parsing or `splitLines`, the
articulation builder, `SingerFace`, `LyricCaption`, the cue scheduler, or
`MenuBandSinger.wordSpans` — which is the one function in the singer explicitly
marked for testing (`MenuBandSinger.swift:284` "also exercised by the offline
regression test") and has no test in this repo.

Every one of those is pure logic with no AppKit dependency. `wordSpans` is
`static` and takes plain values. `SungLine.splitLines` is a string transform.
`SingerPerformance.decode`/`axes` is pure. They are free to test and they are
where the show breaks.

`Package.swift:121-133` makes both test targets depend on the **executable**
`MenuBand` target, so `swift test` relinks the whole app. Extracting a
`MenuBandCore` library target for the pure logic would make the test loop fast
enough to actually run.

# sceneApi 4: GPU-resident meshes

Written 2026-11-12 on the `xbox-bigmap-engine` branch. sceneApi 4 lets a live
JS piece draw a large 3D world without the frame's JavaScript paying for it:
meshes and textures are uploaded once into GPU buffers, and a frame is a few
small calls per chunk or prop. Projection, culling, lighting, skinning and fog
run in C++ and in shaders. Everything older (`triangles3d`, `sceneMesh`,
`meshUpload`/`meshDraw`, `sdfFigure`, the HUD band) is unchanged and still
draws in the same frame, into the same depth buffer.

The design follows ENGINE.md's cost model. On the console the piece runs in
QuickJS with no JIT, and **the count of numbers crossing the boundary is the
cost**. So uploads carry a lot of numbers once, and draws carry a handle, a
27-float camera the piece keeps, and optionally 12 floats of placement.

| file | role |
|---|---|
| `xbox/runtime/include/ac/scene4.hpp` | Shared by every host: caps, the 36-byte vertex, validation and interleaving, smooth normals, skin weights, culling, light masks. |
| `Scene4Bindings.inc` | The QuickJS bindings (`gpu*` globals, `gpuLimits`). |
| `App.cpp` (`CreateMesh4Pipeline` … `DrawGpuMeshes`) | The D3D11 pass. |
| `Mesh4.hlsli`, `Mesh4Vertex.hlsli`, `Mesh4VertexShader.hlsl`, `Mesh4SkinVertexShader.hlsl`, `Mesh4PixelShader.hlsl` | The shaders. |
| `xbox/macos-native/Scene4.swift`, `Scene4Bridge.{h,cpp}`, `Bridge.h` | The Mac shell, in Metal. |
| `tests/scene4_smoke.cpp` | Desk tests: the header's math, the bindings against a probe GPU, and the demo booted under QuickJS. |
| `xbox/live/scene-api-4-demo.js` | A demo that makes every call. |

## Detecting it

```js
const gpu = typeof gpuDraw === "function";           // any host
const level = Number(capabilities().sceneApi) || 0;  // Xbox: 4 when the pass came up, else 3
```

The Xbox reports `sceneApi: 4` only when its GPU pass initialised. If the
shaders are missing from the package, or the device refused a resource, it
reports 3. The `gpu*` functions still exist on a level-3 host, but uploads
return `-1` and draws return `0`. The Mac shell has no `meshDraw`, so it never
advertises a level. Detect it with `typeof gpuDraw`, which is only defined
when the Metal pass is installed (see the Mac section). Resolve this once at
boot and keep the older path as the fallback, as ENGINE.md asks.

`gpuLimits` is a plain object holding the caps below, so a piece can size its
chunks against them rather than against constants.

## The calls

Handles are positive integers, and `-1` means *refused*. A refusal is not an
error: the host has no GPU pass, or a budget is spent. Free something and
try again later. Malformed input is the piece's bug, so it **throws**
(`TypeError` for the wrong kind, `RangeError` for out of range) and nothing
is allocated. A draw with a stale or freed handle returns `0` and does not
throw, because a streamed world races its own frees.

### Meshes

```js
gpuMesh({
  positions: Float32Array,   // xyz per vertex, required
  indices:   Uint16Array | Uint32Array, // whole triangles, required
  normals?:  Float32Array,   // xyz per vertex; omitted → smooth, area-weighted, computed by the host
  colors?:   Uint8Array,     // rgba per vertex (0–255); omitted → white
  uvs?:      Float32Array,   // uv per vertex (texture)
  uvs2?:     Float32Array,   // second uv set (lightmap)
  joints?:   Uint8Array,     // 4 per vertex, each < 64 → a skinned mesh
  weights?:  Float32Array | Uint8Array, // 4 per vertex, required with joints, normalised by the host
  bounds?:   Float32Array(6) // min xyz, max xyz; overrides the computed box
}) → handle | -1
gpuMeshFree(handle) → bool
```

The host interleaves one 36-byte vertex (position f32×3, normal snorm8×4,
colour unorm8×4, uv f32×2, uv2 f32×2). A skinned mesh adds an 8-byte stream
(joints u8×4, weights unorm8×4 summing to 255). Indices are stored as 16-bit
up to 65,535 vertices and 32-bit above that, whatever the piece sent. A mesh
is immutable: to change one, upload a new mesh and free the old.

A **skinned mesh without `bounds` is never culled**, because a pose can leave
its bind-pose box. Give it a box that holds every pose.

### Textures

```js
gpuTexture(width, height, rgba /* Uint8Array, width*height*4 */, flags = 0) → handle | -1
gpuTextureFree(handle) → bool
// flags: 1 mipmaps (generated by the host) · 2 clamp (else repeat) · 4 nearest (else trilinear, 4× anisotropic)
```

Both sides must be powers of two, up to 2048. The format is RGBA8 unorm with
no sRGB conversion, matching every other lane in the renderer. Decode PNGs in
JS, or better, generate textures procedurally at boot. The 2 MiB source cap
applies.

### Materials

```js
gpuMaterial({
  color: [r, g, b, a],   // multiplier, default 1,1,1,1; a < 1 → screen-door transparency
  emissive: [r, g, b],   // added after lighting, default 0
  texture: handle,       // albedo, sampled with uvs
  lightmap: handle,      // sampled with uvs2; replaces ambient + sun
  lightmapScale: 1,      // lightmap rgb × this
  alphaCutoff: 0,        // discard where colour × texture alpha is below this (foliage)
  cull: "none" | "back" | "front", // default "none"; front = counter-clockwise on screen
  unlit: false,          // vertex colour × texture as-is, no lights (baked worlds, skies)
  fog: true,
  depthWrite: true       // false for skies drawn behind everything
}) → handle   // gpuMaterial() gives the defaults
gpuMaterialFree(handle) → bool
```

Materials are small parameter blocks kept by the binding. They hold no GPU
memory and cannot be edited: make a few at boot. A texture handle that has
been freed, or was never valid, draws as white.

### The frame's light

```js
gpuEnvironment(Float32Array(13)) // holds until set again
// 0–2 ambient rgb (.72) · 3–5 sun rgb (.28) · 6–8 fog rgb · 9 fog start · 10 fog end (≤ start: no fog)
// 11 fog max 0–1 (1) · 12 draw distance in view metres (0: unlimited)
gpuLights(Float32Array, count)   // count × 8: x, y, z, radius, r, g, b, 0 — up to 32; holds until set again
gpuLights(null, 0)               // clears
```

The **sun's direction is camera floats 24–26** (the way the light travels),
the same field `meshDraw` already reads. The defaults reproduce `meshDraw`'s
`.72 + .28·max(0, −N·L)`. Lights apply to the whole frame, and each draw is
matched to the lights whose spheres reach its culled world box when the frame
renders. A late `gpuLights` call still applies to every draw in that frame.
The environment is read as each draw is queued (the draw distance culls
there), so set it first in `paint`.

### Drawing

```js
gpuDraw(mesh, material, camera, model = identity, bones) → triangles queued (0: culled or stale)
gpuDrawInstances(mesh, material, camera, instances, count, bones) → triangles queued
gpuStats() → { meshes, meshBytes, textures, textureBytes, materials, draws, culled, triangles, dropped }
```

- `camera` is the existing 27-float native camera: position, right, up,
  forward, screen centre, ortho scale, focal px, perspective blend, near,
  viewport rect, depth base, depth per view metre, sun direction. Keep one
  Float32Array and refill it each frame. A draw copies it, so drawing the
  same mesh with a second camera (an inset, a sky camera) is allowed.
- `model` is 12 floats, the columns of a 3×4 affine matrix: x axis, y axis,
  z axis, origin. Normals use the same 3×3, so keep scale uniform.
- `instances` is `count × 16` floats: 12 of `model`, then an rgba tint that
  multiplies the vertex colour. Instances are culled one at a time on the
  CPU. The survivors become one instanced draw.
- `bones` is required for a skinned mesh and ignored otherwise. It is a
  Float32Array of `n × 12` floats, each the same column layout. Each matrix
  is the *final* skinning matrix (pose × inverse bind), in the mesh's model
  space. `n` must cover the highest joint the mesh uses and be ≤ 64.
  Instances of a skinned draw share its pose.
- The return value is triangles queued after culling. It is useful for the
  same adaptive LOD loop `realm.template.js` runs on its face count.
- `gpuStats()` reports the last frame that queued draws.

Culling uses the mesh's box under each placement. With a perspective camera
(blend ≥ .999) these are exact half-space tests against the near plane, the
four viewport edges and the draw distance, and they hold behind the lens. With
an orthographic or blended camera it is `meshDraw`'s projected-corner test.

## Shading

Per pixel, with the vertex normal interpolated (smooth):

```
base  = vertex colour × instance tint × material colour × texture(uv)
lit   = unlit ? 1
      : (lightmap ? lightmap(uv2) × lightmapScale : ambient + sun × max(0, −N·sunDir))
        + Σ lights reaching this draw: colour × (1 − d²/r²)² × max(0, N·L)
rgb   = base × lit + emissive
rgb   = mix(rgb, fog, clamp((|p − camera| − start) / (end − start)) × fogMax)   // when fog
alpha < 1 → the triangle list's 4×4 screen-door
```

On a two-sided material (`cull: "none"`), a back face lights as if it faced
the viewer. There is no gamma step anywhere, as in the rest of the renderer.
Bloom, grading and any extra fog stay in the live post shader, which reads the
same depth buffer.

## Composing with what is there

- **Depth.** A vertex's depth is `clamp(base + viewZ × slope)`, exactly what
  `meshDraw` and `sceneMesh` write, stored as `(z + 1.5) / 3` in the same
  D24S8 (Xbox) or depth32 (Mac) buffer. GPU meshes, triangles, SDF figures and
  raycast sprites therefore occlude each other correctly in any order. Within
  a triangle, depth interpolates linearly in screen space between its
  vertices, as it does for the triangle list. Very long triangles meeting at
  a steep angle can intersect a little off; tessellated terrain is fine.
- **Perspective.** With a pure perspective camera, positions are emitted in
  homogeneous form (w = view depth). Clipping at the near plane and texture
  and colour interpolation are therefore exact. With blended cameras each
  vertex is projected exactly and interpolated affinely, which is what the CPU
  path does. Avoid geometry that crosses the near plane under a mid blend.
- **HUD band.** GPU mesh depth is clamped to −1.455…1.4, so a world mesh can
  never be read as HUD (z ≤ −1.46) by the post pass's sharp mask. The HUD
  stays on `triangles3d` with z ≤ −1.47 and text, drawn after post as before.
  GPU meshes cannot draw in the HUD band. A 3D HUD model needs either an
  overlay flag or a second post-pass draw list (open question 4).
- **Order.** On the Xbox the pass runs after the depth clear and before the
  world triangles. On the Mac it runs after the triangle batch, inside the
  same world encoder. Opaque results do not depend on the order. Draws run in
  submission order, so submit near chunks first if overdraw matters.
- **Stencil and post.** Xbox draws write stencil 1 like the triangle list, so
  post's second (FXAA/tilt) pass covers them. A sky material with
  `depthWrite: false` still writes stencil.
- **Viewport.** The camera's viewport rect (floats 18–21) becomes a scissor
  rect, so split-screen views clip exactly as `meshDraw` does.
- **Sky.** Draw a dome with its own camera at the origin, depth base 1.395 and
  slope 0 (the realm's `SKYCAM`), using an `unlit`, `fog: false`,
  `depthWrite: false` material.

## Budgets

| cap | value | where |
|---|---|---|
| vertices / indices per mesh | 1,048,576 / 3,145,728 | upload |
| all live mesh memory | 192 MiB (vertex + skin + index bytes) | upload → `-1` |
| all live texture memory | 128 MiB (mips count 4/3) | upload → `-1` |
| texture side | 2048, power of two | upload → throws |
| live meshes / textures / materials | 4096 / 1024 / 4096 | upload → `-1` |
| bones per draw | 64 | draw → throws |
| point lights | 32 a frame | `gpuLights` → throws |
| draws a frame | 4096 | draw → `0`, `dropped` |
| instances a frame | 65,536 | draw → `0`, `dropped` |
| bone matrices a frame | 16,384 | draw → `0`, `dropped` |

The per-frame Xbox resources are fixed at startup: a 4 MiB instance buffer
and a 768 KiB bone buffer. The mesh and texture caps are a soft ceiling chosen
to sit well inside an Xbox UWP title's GPU-visible memory. They are not
measured on hardware. Read `capabilities().memoryUsageBytes` and
`memoryLimitBytes` against them.

Uploads are copied, so a piece can (and on QuickJS should) reuse one scratch
`Float32Array`/`Uint8Array` per chunk shape. The JS heap is capped at 32 MiB
and the source at 2 MiB, so a big world is generated at boot or decoded from
compact binary, never shipped as vertex literals.

### Streaming a big map

1. Cut the world into square chunks, for example 32×32 cells. Every chunk
   with the same grid shares one index array, so build it once and pass the
   same `Uint16Array` to every upload.
2. Each frame, free the chunks past a radius and upload at most one or two
   new ones. An upload is a QuickJS fill plus a buffer copy, so this spreads
   the cost and avoids a hitch on a turn. The demo does exactly this:
   ~150 chunks live, ~7 MB.
3. For LOD, upload each chunk at two or three steps and pick one per frame by
   distance, as `realm.template.js` does today. Skirts hide the seams. Free
   the fine LOD of far chunks if memory matters.
4. Use the draw distance and fog together. Culling at `drawDistance` is free,
   and fog that reaches `fogMax` = 1 before it hides the pop-in.
5. Draw props with `gpuDrawInstances` (trees, rocks, lamps). A culled
   instance costs a box test in C++, not a JS write.
6. Watch `gpuStats()`: `meshBytes` against `gpuLimits.meshBytes`, and
   `dropped` for draws refused because the frame's budget was spent.

### Characters

Baked-frame characters (`realm.template.js`'s hero and frogs) cost tens of
thousands of JS float writes a frame on QuickJS. On sceneApi 4 they become a
skinned mesh uploaded once, plus a 64×12-float palette a frame, which is
about 0.2 ms of QuickJS per character. The skinning, lighting and shading
run on the GPU. To get under even that, the next step is clips on the host
(open question 1).

### Ownership

Every handle belongs to the piece that made it. When a piece's JS context is
destroyed (reload, `pieceReboot`, a rollback that retires it), the binding
frees everything it still holds. A frame that queued a draw keeps the mesh
alive until that frame has rendered, so a free in the middle of `paint` is
safe.

## The Xbox renderer

`CreateMesh4Pipeline` compiles nothing at runtime. It loads three `.cso`
files built from the HLSL by the project's FxCompile items (both the UWP and
the GDK vcxproj list them) and creates the following:

- input layouts for the static and skinned vertices
- three constant buffers: view per camera, scene per frame, draw per draw
- dynamic structured buffers for the instance and bone palettes
- a 1×1 white texture
- three rasterizer states (none/back/front, counter-clockwise front, scissor
  on)
- four samplers (wrap/clamp × trilinear-anisotropic/point)

Mesh and index buffers are `D3D11_USAGE_IMMUTABLE`. Mipmapped textures are
created with `GENERATE_MIPS` and filled by `GenerateMips` at upload. Draws
are queued in `QueueMesh4`, which copies the camera, culls instances into the
frame's instance list, and appends bone rows. `DrawGpuMeshes` then uploads
the palettes once, sets per-frame state once, and issues one
`DrawIndexedInstanced` per queued draw, changing view constants only when the
camera changes. `Render()` now also wakes for a frame that holds only GPU
draws. `AC_NATIVE_PROFILE` gains `mesh4Draws`, `mesh4Triangles`, `mesh4Bytes`
and `texture4Bytes`, and `AC_NATIVE_MESH4 ready=1 …` logs once at startup.

## The Mac shell

`Scene4.swift` is the same pass in Metal. It uses the same caps and the same
vertex layout, and its MSL is a line-for-line copy of the HLSL. It reaches the
shared C++ (validation, culling, light masks) through `Scene4Bridge`, so both
hosts accept, reject and cull the same data. It is compiled in with
`-D SCENE4` by `xbox/tools/build-macos-app.sh`. The App Store project
(`apple/oskiewar-mac`) builds without the flag and is unchanged.

The Metal renderer, `MetalSceneView`, lives in the private vault
(`apple/oskiewar/Sources`). It has no way to add a pass, so sceneApi 4 needs
one small hook there:

```swift
@objc var worldPass: ((MTLRenderCommandEncoder, CGSize) -> Void)?   // property
worldPass?(encoder, drawableSize)   // in draw(in:), after the triangle batch, before the SDF figures
```

`Scene4.attach` looks the hook up at runtime (`setWorldPass:`). With the hook,
the `gpu*` globals install and draw inside the world encoder, depth attached
and ink outlines included. Without it, the shell logs
`scene4 unavailable: MetalSceneView has no worldPass hook` and defines nothing,
so the piece takes its older path. The pass restores cull mode, winding and
scissor before it hands the encoder back. Per-frame instance and bone data
ride a ring of four buffers, and the shell keeps at most three frames in
flight. Every `wipe()` starts a new frame on the Mac, as it does for the Mac's
triangle list, so call `wipe` before drawing.

## Open questions

1. **Clips on the host.** Should skinned characters get `gpuClip(frames,
   boneCount)` and `gpuDraw(…, clip, time)`, so the host samples and blends
   poses and a character costs two numbers a frame instead of 768? It is
   cheap in C++, and it is the same "builder in C++" lesson ENGINE.md draws
   for instancing.
2. **Dynamic vertex data.** Baked-frame (morph) characters and water could
   use `gpuMeshUpdate(handle, positions)` with a dynamic buffer. It was left
   out to keep meshes immutable. Is skinning enough?
3. **Shadows.** There is no shadow map. Baked lightmaps and vertex colours
   cover static worlds. A single cascaded sun shadow for characters would be
   the next renderer feature.
4. **HUD-band 3D.** Should a material flag let a GPU mesh draw after post in
   the overlay band (spinning pickups in a menu)?
5. **Mac without the hook.** Should the Mac fall back to a CPU path through
   `triangles3d` (flat per face, textures sampled at centroids) when the vault
   renderer lacks `worldPass`? Today it simply reports no sceneApi 4.
6. **Far from the origin.** Vertex positions are float32 in world space, and
   the vertex shader subtracts the camera there. Past about ±16 km, motion
   will visibly jitter. A map that size would need a per-chunk origin (an
   `origin` in the model matrix, made camera-relative on the CPU in double
   precision). The linear `(z + 1.5) / 3` depth is not the limit: in D24 it
   resolves about 0.05 mm over a 700 m span.
7. **Mac capability level.** Should `capabilities()` on the Mac advertise a
   per-feature map (`{gpuMeshes: true}`) rather than a level? The levels
   assume `meshDraw`, which the Mac lacks.
